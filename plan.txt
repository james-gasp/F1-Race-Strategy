# F1 Race Strategy Simulator — Build Plan

## Context

This project is being built as a portfolio piece to support internship applications to Visa Cash App Racing Bulls (VCARB) F1 Team across three roles: **Software Engineering**, **Race Strategy**, and **Data Science**. The repo (`F1-Race-Strategy`) is currently empty — this is a from-scratch build.

The goal is a project that isn't just "a lap-time calculator" but demonstrates the full stack each role cares about:
- **Race Strategy**: real strategy modeling — undercut/overcut, pit windows, safety car risk, competitor reaction — matching their posting's "develop and enhance strategy simulation tools" bullet almost verbatim.
- **Data Science**: real telemetry data (via FastF1), statistical/ML modeling of tire degradation, Monte Carlo simulation over uncertainty, not hand-waved constants.
- **Software Engineering**: a properly separated, typed, tested system (FastAPI backend + React/TypeScript frontend) — mirroring their actual listed stack (C#/TypeScript/React/Python), not a single-file Streamlit notebook-app.

Decisions locked in during planning:
- **Interface**: Interactive web dashboard.
- **Data source**: FastF1 real historical telemetry, used to calibrate/fit parametric models (not pulled live per-simulation — fit once, simulate fast on the fitted model).
- **Scope**: Go big — full-featured build, phased so there's always a working demo at each checkpoint before the Oct 4, 2026 application deadline.
- **Standout feature (core, in MVP)**: Competitor/field modeling — simulate the whole field's likely strategies so outputs are finishing-position probabilities, not just one car's lap time. This is the feature that makes it "strategy" instead of "lap-time math."
- **Stretch differentiators (phase 3, pick up if time allows)**: historical backtesting/"what-if" replay, ML tire degradation model with explainability (SHAP), safety car/VSC probability modeling feeding into the optimizer.
- **Tech stack**: FastAPI backend + React/TypeScript frontend, **built in that order** — simulation engine + API complete and tested first (usable/demoable via Swagger UI alone), React layered on top after. This protects the project against running out of time before the deadline: worst case, you still have a working, demoable API-driven engine even with a thin or unfinished frontend.

## Architecture Overview

```
f1-race-strategy/
├── engine/                 # Pure Python simulation core (no web deps) — this is the heart of the DS/strategy work
│   ├── data/                # FastF1 data loading + caching + cleaning
│   ├── models/               # Tire degradation, fuel effect, pit-loss, lap time models
│   ├── strategy/             # Strategy representation, Monte Carlo race simulator, competitor/field model
│   ├── optimize/              # Strategy search/optimizer (given current race state, best pit lap+compound)
│   └── tests/                # pytest unit tests on the engine — this is what should be rock solid
├── api/                    # FastAPI app exposing the engine
│   ├── routers/              # /races, /simulate, /strategy/optimize, /compare
│   ├── schemas/               # Pydantic request/response models (typed contract with frontend)
│   └── tests/                 # API integration tests
├── frontend/                # React + TypeScript (Vite), consumes the API
│   └── src/
│       ├── api/                # typed API client generated/matched from Pydantic schemas
│       ├── components/          # race selector, strategy builder, results charts
│       └── pages/                # dashboard views
└── notebooks/                # exploratory FastF1 analysis, model fitting/validation (throwaway, not shipped code)
```

Why this split: `engine/` has zero web/framework dependencies, so it's independently testable and is the part that actually proves DS/strategy competence — a reviewer can read it without wading through API or UI code. `api/` is a thin, typed contract layer (this is the "software engineering" proof point: clean boundaries, Pydantic validation, tests). `frontend/` is presentation, built last so it never blocks having a working product.

## Phased Build Plan

### Phase 0 — Project scaffold (few hours)
- `uv`/`poetry`-managed Python project for `engine/` + `api/`, `pytest` configured.
- Vite + React + TypeScript scaffold for `frontend/` (not wired to real data yet).
- FastF1 installed, cache directory configured, confirm you can pull one real session's laps/tire/pit data end-to-end.
- Basic CI (GitHub Actions running pytest) — cheap, signals SWE rigor immediately.

### Phase 1 — Simulation engine MVP (core deliverable)
1. **Data layer** (`engine/data/`): FastF1 loader for a given race → clean lap-by-lap DataFrame (lap time, compound, tire age, stint, pit laps, track status/SC flags).
2. **Lap time model** (`engine/models/`): fit a parametric model per compound: `lap_time = base_pace + tire_deg(tire_age, compound) + fuel_effect(laps_remaining) + noise`. Fit degradation curves from real data per track (start simple: linear/quadratic fit; this is your baseline before the ML stretch version).
3. **Pit loss model**: track-specific pit lane time loss, fit from real pit-in/pit-out lap deltas.
4. **Single-car Monte Carlo simulator** (`engine/strategy/`): given a strategy (compound sequence + pit laps), simulate N races with noise/variance sampled from the fitted residuals, output a distribution of total race time.
5. **Strategy comparison**: run 2+ strategies through the simulator, compare distributions (this alone is already a legitimate "strategy simulator").
6. Unit tests on all of the above — deterministic where possible, statistical sanity checks (e.g. degradation is monotonic, more laps on old tires ⇒ slower) elsewhere.

**Checkpoint**: at this point you have a working, tested, demoable core even with zero UI (runnable from a notebook or `pytest` output showing strategy A beats strategy B by X seconds with confidence bounds).

### Phase 2 — Competitor/field modeling + API (the differentiator)
1. **Field model** (`engine/strategy/field.py`): represent the full grid's starting state (grid position, tire choice) and give each competitor a strategy (from real historical data, or a simple heuristic policy).
2. **Race-level Monte Carlo**: simulate the whole field together — lap time model + pit strategies + basic overtaking/traffic model (even a simplified probabilistic overtake model based on pace delta is enough — don't over-engineer this part) — output **finishing position probability distributions**, not just lap time. This is the key differentiator vs. generic "undercut calculator" projects.
3. **Strategy optimizer** (`engine/optimize/`): given current race state (lap, gaps, tire ages), search over candidate strategies (grid search or simple Bayesian/genetic optimizer) to recommend the pit lap + compound that maximizes expected finishing position / minimizes expected race time.
4. **FastAPI layer**: wrap the above in typed endpoints — `POST /simulate`, `POST /strategy/compare`, `POST /strategy/optimize`, `GET /races/{year}/{round}`. Pydantic schemas double as the frontend's type contract. API integration tests.

**Checkpoint**: fully working, demoable product via Swagger UI (`/docs`) alone — this is your fallback safety net if frontend time runs short.

### Phase 3 — React/TypeScript dashboard
- Race/session selector (pulls from FastF1-backed endpoint).
- Strategy builder UI (choose compounds + pit laps, or let the optimizer suggest one).
- Results visualization: race time distribution (histogram/violin), finishing position probability chart, gap-to-leader over time for a chosen strategy vs. field.
- "Live-ish" mode: step through a real historical race lap by lap, show the optimizer's recommendation at each point vs. what actually happened (this doubles as a soft version of the backtesting stretch feature).

### Phase 4 — Stretch differentiators (time permitting, pick based on remaining runway)
Pick 1–2 of these, don't try all three under time pressure:
- **Historical backtesting/replay**: replay a real race's actual strategy vs. your optimizer's recommended strategy, report the counterfactual (positions gained/lost). Strong narrative for a cover letter/README.
- **ML tire degradation model + explainability**: replace the linear/quadratic fit with a gradient-boosted model (track temp, fuel load, driver, compound → deg rate), show SHAP feature importance in the dashboard. Strongest pure Data Science signal.
- **Safety car/VSC probability modeling**: per-track historical SC/VSC frequency → inject probabilistically into the Monte Carlo, show how it shifts optimal pit lap (e.g. "pit under SC" value calculation). This is one of the biggest real levers in actual strategy calls and rarely done in hobby projects.

## Key Technical Notes
- **FastF1**: cache aggressively (`fastf1.Cache.enable_cache(...)`) — don't re-fetch per simulation run; fit models once, store fitted parameters, simulate against those.
- **Monte Carlo scale**: thousands of simulated races per strategy comparison should run in well under a second in pure numpy/pandas — vectorize rather than looping in Python where possible; this matters for both UX (interactive dashboard) and for the optimizer (which needs many simulation calls).
- **Testing priority**: `engine/` gets the most rigorous tests (this is what a technical reviewer will actually read closely). API and frontend get standard integration/smoke tests.
- **README**: given this is portfolio-driving, the README should lead with the competitor-modeling + optimizer result (a concrete example: "for Track X, our optimizer recommends pitting lap N for compound Y, improving expected finish by Z positions vs. the field-median strategy") — a recruiter skims the README before running anything.

## Verification
- `engine/`: `pytest` with unit tests per model (degradation monotonicity, pit loss sanity, Monte Carlo convergence checks) and at least one integration test simulating a full real race end-to-end against FastF1 data.
- `api/`: integration tests hitting each endpoint with a real (small/cached) race, asserting schema-valid responses.
- `frontend/`: manually exercise the dashboard against a running local API (`preview_start`/browser check) for the golden path (select race → build strategy → view results) and at least one edge case (invalid strategy, race with no SC data).
- End-to-end demo check before considering a phase "done": can you, from a clean checkout, run one command to stand up the API + frontend and get a real result for a real race?
